Phase-by-Phase Deep Dive

Phase 1 — Pod Scheduling & Webhook Injection (~5–15s)

The Kubernetes default scheduler evaluates nodeSelector, taints/tolerations, and resource requests. For GLM 5.1 700B FP8 with TP=8, the pod must land on a node with nvidia.com/gpu: 8 available and sufficient CPU/memory for the init container and vLLM process (~128 Gi RAM request typical).

KServe's mutating admission webhook (kserve-webhook-server) intercepts Pod creation for InferenceService-managed workloads. It injects:

  • Storage Initializer init container (kserve/storage-initializer)
  • Model volume mount at /mnt/models
  • Environment variables: STORAGE_URI, credential mounts for S3
  • Sidecar containers if configured (e.g., Istio, agent)

Phase 3 — Weight Loading: Disk → CPU (~15–120s)

vLLM's BaseModelLoader.load_model() orchestrates the four-step pipeline shown above. Each TP rank loads only its shard via the safetensors streaming iterator — no rank reads the full 860 GB.

Per-rank data size formula:

bytes_per_rank = model_size_bytes / tp_size
                 = 860 × 10⁹ / 8
                 ≈ 107.5 GB per rank
Safetensors StrategyI/O PatternNFS (1.5 GB/s)NVMe (6.5 GB/s/rank)When to Use
lazy (default)mmap + on-demand page faults60+ min (random I/O)~20sLocal SSD only
prefetchSequential read entire shard to RAM~72s per rank~16s per rankAlways on NFS
eagerLoad all tensors synchronously at initSimilar to prefetch~16sSmall models
torchaoQuantized load pathVariesVariesINT4/FP8 checkpoints

Streaming iterator mechanism: SafetensorsLoader opens each *.safetensors file, iterates tensor metadata headers, filters keys matching the current TP rank's shard map (weight_loader callbacks), and copies only matching tensors into pre-allocated meta-device buffers. Overlaps disk read with tensor deserialization via Python generator — peak RAM ≈ 1.2× shard size during load.

Safetensors Load Strategy is Critical

DeepSeek-V4-Pro 805 GiB on NFS: lazy stalled 60+ minutes. Switching to --safetensors-load-strategy prefetch reduced to ~12 minutes. Always use prefetch for network filesystems.

Phase 4 — CPU → GPU Transfer + NCCL Init (~5–20s)

After CPU-side load, PyTorch copies weights to GPU VRAM via tensor.cuda() / pinned memory DMA. All 8 ranks transfer in parallel — each rank moves ~107 GB independently.

PCIe Gen5 bandwidth formula:

transfer_time = bytes_per_rank / pcie_bandwidth
              = 107.5 × 10⁹ / (64 × 10⁹)   # 64 GB/s bidirectional per GPU
              ≈ 1.68 s per rank (theoretical)
              ≈ 3–5 s observed (driver overhead, pinned alloc)

NCCL initialization (Tensor Parallel AllReduce setup):

  • ncclCommInitRank() — creates communicator for TP group (8 GPUs)
  • Topology detection via NVML: NVSwitch full-mesh on p5en (no PCIe hops between GPUs)
  • Algorithm selection: NVLS (NVLink Sharp) for AllReduce when available
  • Buffer registration: ~512 MB scratch per rank for AllReduce staging
  • Typical init time on 8×H200 NVSwitch: 1–3 seconds

Phase 5 — torch.compile + CUDA Graph Capture (~120–180s) — THE FLOOR

Purely compute-bound. No I/O optimization can reduce this phase. vLLM enables both by default in recent versions.

Sub-phaseMechanismLlama 70B (TP=8)GLM 5.1 700B (est.)
torch.compile / DynamoFX graph capture → Inductor Triton codegen~70s~90–150s
CUDA graph capture67 graphs, batch sizes 1–256~60s~60–90s
Warmup forward passesKernel JIT + memory pool alloc~10s~15–20s

CUDA Graph capture detail: vLLM captures 67 CUDA graphs covering batch sizes in range [1, 2, 4, 8, 16, 32, 64, 128, 256] plus padding variants. Each graph freezes the kernel launch sequence for a fixed batch shape — eliminating Python overhead per decode step. Capture runs dummy forward passes; memory for graph pool pre-allocated (~2 GB per rank).

torch.compile Dynamo internals: TorchDynamo intercepts Python bytecode at frame entry, builds FX graph of ATen ops, passes to Inductor backend which generates fused Triton kernels. For 700B: ~180 transformer layers × attention + MLP subgraphs. Dynamo guard checks recompile on shape change. fullgraph=True not used — partial graph with graph breaks at custom ops.

Emerging: CUDA Checkpoint/Restore (RFC #34303)

Snapshots entire GPU state (weights + KV cache layout + CUDA graph handles) to NVMe via cuCheckpointSave() / cuCheckpointRestore(). Qwen3-235B cold-start: 10 min → 3.9 seconds. Requires identical driver/CUDA version at save and restore. Still RFC-stage — not in stable vLLM or RHOAI 3.4. Implication: future scale-up could skip Phases 3–5 entirely with pre-warmed checkpoints.

Module 3

Network Topology for Multi-GPU Inference

Interconnect bandwidth is the bottleneck for tensor-parallel inference at scale. The hierarchy on p5en: NVSwitch (900 GB/s) → EFA RDMA (400 GB/s) → PCIe Gen5 (64 GB/s) → pod TCP (12.5 GB/s). TP=8 must stay inside the NVSwitch domain; PP/EP across nodes requires EFA + GPUDirect RDMA.

Intra-Node: 8× H200 NVSwitch Topology (p5en)

Single p5en node: 8× H200 connected via central NVSwitch — mandatory domain for TP=8 on 700B models.

Inter-Node: EFA Topology (2× p5en)

Two p5en nodes connected via EFAv3 (3200 Gbps aggregate) for pipeline/expert parallelism across nodes.

TP AllReduce Bandwidth Calculation

Each transformer layer performs AllReduce on activation tensors. Data moved per layer per forward pass:

bytes_per_allreduce = (batch × seq_len × hidden_dim × dtype_bytes × 2) / tp_size

# GLM 5.1 700B: hidden_dim ≈ 8192, FP16 activations (2 bytes), TP=8, batch=1, seq=1 (decode)
bytes = (1 × 1 × 8192 × 2 × 2) / 8 = 4,096 bytes per layer (decode step)

# Prefill (seq=4096):
bytes = (1 × 4096 × 8192 × 2 × 2) / 8 = 16,777,216 bytes ≈ 16 MB per layer

# Total per forward pass (80 layers, prefill seq=4096):
total = 16 MB × 80 layers = 1.28 GB AllReduce traffic per GPU per prefill

GPUDirect RDMA Bypass Mechanism

Without GPUDirect Standard Path

GPU VRAM → PCIe → CPU pinned buffer → kernel TCP/UDP stack → NIC → network → NIC → CPU buffer → PCIe → GPU VRAM. 4 memory copies, CPU-bound, ~12.5 GB/s effective on pod network.

With GPUDirect RDMA Bypass Path

GPU VRAM → NVLink → GPU BAR → EFA NIC RDMA engine → EFA fabric → peer NIC → peer GPU VRAM. Zero CPU involvement. NCCL uses NET/IB/GDRDMA transport. Requires nvidia-peermem kernel module + NCCL_NET_GDR_LEVEL=5.

Intra-Node: NVLink/NVSwitch (8× H200)

900 GB/s per link via 4th-gen NVLink (NV18 in topo matrix). Full bisection bandwidth — any GPU pair communicates at line rate. TP=8 AllReduce uses NCCL NVLS (NVLink Sharp) for in-switch reduction when available, halving data movement.

Processing a single 70B query (80 layers, decode): ~20 GB cumulative AllReduce traffic per GPU — completes in <25 ms on NVSwitch vs ~1.6 s on PCIe-only topology.

Inter-Node: EFA + GPUDirect RDMA

3200 Gbps (400 GB/s) via EFAv3. Both p5en instances must be in the same cluster placement group for <10 µs latency. Pod spec requires:

resources:
  limits:
    vpc.amazonaws.com/efa: "1"
annotations:
  k8s.v1.cni.cncf.io/networks: gpu-workloads/efa-network

Red Hat benchmarks: 3× throughput over default OVN-Kubernetes pod networking for PP=2 workloads.

llm-d Disaggregation Topologies

Production EPD (Default)

Single worker: encode + prefill + decode colocated. Simplest. No NIXL transfer overhead. Best for low-concurrency or models < 70B.

Production P/D (Prefill/Decode)

Separate pools. Prefill workers handle compute-heavy prompt processing; decode workers optimized for memory bandwidth. NIXL KV transfer between pools. Tested nightly on OCP.

Experimental E/PD

Dedicated encode workers for multimodal (vision/audio). Text prefill-decode workers receive pre-encoded embeddings.

Experimental E/P/D (Full 3-Stage)

Maximum specialization. Highest throughput potential at cost of 3× infrastructure complexity and 2 NIXL transfer hops.

Runtime Upgrade Procedure

STEP 1 Update ServingRuntime image/args

Platform admin patches the cluster-scoped ServingRuntime: new vLLM image tag, updated default args. Does not trigger pod restart — existing InferenceServices unaffected until step 2.

STEP 2 Rolling-update InferenceServices

Add annotation serving.kserve.io/restart: "true" or patch a harmless spec field (e.g., env var) on each InferenceService. KServe controller detects drift and initiates rolling update per deploymentStrategy.

STEP 3 Monitor cold-start on new pods

oc get inferenceservice glm-5-1-700b-fp8 -o jsonpath='{.status.conditions}'. Watch for Ready=True on new revision. StartupProbe allows 10 min for 700B compile phase.

STEP 4 Verify traffic cutover

Confirm old pod terminated: oc get pods -l serving.kserve.io/inferenceservice=glm-5-1-700b-fp8. Run smoke test: curl $ROUTE/v1/chat/completions -d '{"model":"glm-5.1","messages":[{"role":"user","content":"ping"}]}'

ROLLBACK Revert if regression detected

Revert ServingRuntime image tag → re-trigger restart annotation. Rolling update brings back previous runtime. With LocalModelCache: rollback cold-start ≈ 4 min (no re-download).

Rolling Update for 700B Models

Requires both p5en nodes simultaneously: old replica on Node 1 serves traffic while new replica cold-starts on Node 2. Budget 4–5 minutes and 16× H200 during transition. This is why the cluster spec includes 2× p5en.48xlarge.

Multi-Engine Operation

A single cluster runs vLLM for LLMs on GPU nodes + OpenVINO for classical ML on CPU infra nodes. Triton can be added as a Tested & Verified custom runtime for ensemble pipelines. Each InferenceService targets its runtime via spec.predictor.model.runtime or auto-selection via supportedModelFormats.

KV Cache Memory Formula

Formula
KV_bytes/token/layer/GPU = 2 × num_kv_heads × head_dim × dtype_bytes

KV_bytes/token/GPU       = KV_bytes/token/layer/GPU × num_layers
KV_bytes/token/cluster   = KV_bytes/token/GPU × tensor_parallel_size

APC Hash Chain — Shared System Prompt

# block_size = 16 tokens
hash(block_0) = xxhash("" + tokens[0:15])
hash(block_1) = xxhash(hash(block_0) + tokens[16:31])
hash(block_2) = xxhash(hash(block_1) + tokens[32:47])
# ... chain continues for full prefix

# Two requests with identical 512-token system prompt:
# Request A: [system_prompt(512)] + [user_query_A]
# Request B: [system_prompt(512)] + [user_query_B]
# → blocks 0–31 share identical hashes → ref_count=2 on same physical blocks
# → only user-specific suffix blocks allocated separately

CPU Offloading — Lazy vs Eager, LRU vs ARC

Transfer Mode

Lazy (default): Blocks copied to CPU only on GPU eviction. Minimizes PCIe traffic when working set fits in VRAM.

Eager: Proactively pre-warms CPU tier for predicted long contexts. Higher PCIe use, lower TTFT on cache hit from CPU.

Eviction Policy

LRU: Evicts least-recently-used block. Simple, predictable. Default in RHOAI v0.16.

ARC: Adaptive Replacement Cache — balances recency and frequency partitions. Better for mixed scan/rescan workloads. Upstream vLLM main only.

Benchmark — Llama-3.1-8B CPU Offload

Published vLLM v0.19 benchmarks: <1% throughput impact when active working set fits GPU; 176 ms TTFT on CPU cache hit vs full prefill recompute (~2–5 s). PCIe Gen5 @ 64 GB/s → ~2 µs per 128 KiB block transfer.

MPS — throughput vs isolation trade-off

MPS allows multiple processes to submit kernels concurrently without context-switch overhead. Throughput can increase 1.3–1.8× vs time-slicing for batch workloads. Not recommended when tenants require memory isolation — one OOM affects all clients on the GPU.

700B Model Tenancy Note

GLM 5.1 700B FP8 consumes all 8× H200 on one node (TP=8). Multi-tenancy for this model is access-control isolation (MaaS tiers, RBAC), not GPU sharing. Use MIG/time-slicing on the g5 node for 7B–14B tenant workloads.
